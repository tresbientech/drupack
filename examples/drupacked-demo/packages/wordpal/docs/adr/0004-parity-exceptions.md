# Parity exceptions

**Markup parity**'s contract ignores text, HTML-sourced attribute values, the layout hash, and a class or attribute only Drupal prints. Every other difference between a Drupal page and its **Reference render** is real, and `MarkupComparator` reports it.

Classes and attributes compare one way. Each class and attribute WordPress prints must be on Drupal's side, with the same value. Inline styles compare both ways, and an element only Drupal prints stays reported. Owner ruling, 2026-09-30: a visual check of five themes traced visible defects to Drupal-only elements and none to a Drupal-only class or attribute. Theme CSS and scripts select on the classes and attributes WordPress prints.

Five contract rules follow from ignoring text, saved values and CSS text:

- Unclassed inline formatting tags (`em`, `strong`, `span`, `br` and the others in `MarkupComparator::INLINE_FORMATTING`) drop out with the sample text they format. A tag that wraps a structural element stays compared.
- An `href` and a video `poster` compare for presence, because each site prints its own URLs.
- A `background-image` declaration compares as `url(SOURCE)`, because saved WordPress markup supplies the image URL. The other background declarations stay compared.
- Inline declarations compare as CSS reads them: `0px` compares as `0`, and a repeated declaration counts once.
- A `<style>` element in the page body drops out. A plugin or a Frozen block prints CSS there, and the element draws no box. The computed-style comparison (ADR 0017) checks the rules it holds.

Generated suffixes need one more rule. WordPress's `wp_unique_id()` numbers `wp-elements-N` and `is-style-<variant>--N` classes, the navigation overlay's `modal-N` id, the accordion item's `accordion-item-N` id, the Search block's `wp-block-search__input-N` input id and the Archives and Categories dropdown's `wp-block-archives-N`/`wp-block-categories-N` label and select ids per request, like the layout container hash. Drupal's `Html::getUniqueId()` suffixes the Search input id and the Archives and Categories dropdown ids per request too. Only the generated part normalizes. The class prefix and the variant name stay significant, the overlay ids compare as `modal-ID` and `modal-ID-content`, the accordion ids in `id`, `aria-controls`, `aria-labelledby` and `data-wp-context` compare as `accordion-item-ID`, the Search input's `id` and its label's `for` compare as `wp-block-search__input-ID`, and a dropdown's `id`/`for` compare as `wp-block-archives-ID` or `wp-block-categories-ID`.

Further exceptions stay below, each scoped to one place where Drupal and WordPress cannot produce the same markup:

- Comment form field names differ: WordPress ids and names fields `author`, `email`, `url`, `comment`, `submit`. Drupal uses `name`/`edit-name`, `mail`/`edit-mail`, `homepage`/`edit-homepage`, `comment_body[0][value]`/`edit-comment-body-0-value`, `op`/`edit-submit`. Both sides normalize to the WordPress names.
- Hidden form controls differ: each platform's comment handler reads its own hidden inputs. Drupal's Form API sends `form_build_id`, `form_token` and `form_id`. WordPress sends `comment_post_ID` and `comment_parent`, because its form posts to one shared handler. Drupal's comment reply route carries the node and parent comment instead. These five inputs drop out, and any other hidden input is compared. Each form posts to its own route, so `action` compares for presence only.
- Storage-length attributes differ: Drupal sets `maxlength` from the comment body's field storage schema; WordPress sets none. Compared only for presence.
- Numeric entity IDs differ: WordPress and Drupal number posts, terms and comments independently. The `post-<ID>` class, a Tag Cloud link's `tag-link-<ID>` class, a Categories item's `cat-item-<ID>` class, a Media & Text image's `wp-image-<ID>` class, a Query row's `post-template-item-<ID>` key, a comment `<li>`'s `comment-<ID>` id, and a comment link's `data-commentid`, `data-postid` and `data-belowelement` attributes normalize to a placeholder. Other post classes stay significant.
- Drupal form wrappers differ: Drupal's Field API renders an empty `field--name-langcode` div on the comment form, and CKEditor wraps the comment body textarea in an unclassed div. Scoped to the comment form.
- Boolean attributes serialize differently: WordPress writes `required` with no value; Drupal writes `required="required"`. Scoped to the comment form.
- A cookie-consent checkbox differs: `comment_form()` prints a `comment-form-cookies-consent` paragraph, checkbox and label when the site's `show_comments_cookies_opt_in` option is on, WordPress's own default. Drupal core's comment form has no cookie-consent control. Scoped to the `comment-form-cookies-consent` paragraph and its checkbox and label, inside the comment form.
- Gallery instance classes differ: WordPress adds a `wp-block-gallery-<n>` class from `wp_unique_id()` to each gallery, for a gap rule it prints in the page head. WordPal writes the gap as layout CSS instead, so the class drops out. Scoped to the gallery `<figure>`.
- An unregistered duotone preset differs: `WP_Duotone::render_duotone_support()` only classes an element `wp-duotone-<slug>` for a `var:preset|duotone|<slug>` reference the theme's `theme.json` registers. An unregistered slug falls through to the block's CSS-string path, which strips the reference's colons and pipes and numbers it per request instead: `wp-duotone-varpresetduotone<slug>-<n>`. WordPal always treats the reference as registered. Scoped to that generated class, on a WordPress element whose Drupal side carries `wp-duotone-<slug>`.
- Time zones differ: each site renders dates in its own configured time zone. A `<time>` element's `datetime` compares as the instant it names.
- The deprecated `core/post-comments` block's comment items differ: WordPress renders each one through the classic `Walker_Comment::html5_comment()` markup, an `article` with a `comment-meta` footer and a `vcard` author `div`. WordPal's Comment Template renders each comment through its own per-block fragments instead: avatar, author name, date, content, edit link and reply link, the shape `core/comments`'s current, non-legacy save produces. Scoped to a `core/post-comments` comment list's `<li>` children, once its wrapper, heading and list element already convert to the current save (see the older saved formats exception below).
- Comment and author avatars differ: WordPress falls back to a Gravatar `<img>` when the author has no picture. Drupal renders an `<img>` only when the author has a `user_picture`. A `wp-block-avatar` element, in a comment or as an Avatar block, and the Author block's `wp-block-post-author__avatar` element skip their image comparison only when Drupal renders no image. An Avatar block's image may sit in its author link. A Latest Comments item drops WordPress's avatar image when Drupal prints none. The computed-style comparison (ADR 0017) skips the same image, and the box geometry of the avatar container and the rest of its block instance, which cannot match once the missing avatar collapses the container's own box. Gravatar avatars come from the contrib module Avatar Kit (`drupal/avatars`), whose latest release (8.x-1.3) declares `^9.5 || ^10` and has no Drupal 11 release yet. The `gravatar` project has Drupal 7 releases only.
- The Search form's target differs: WordPress submits `s` to the site root, an absolute URL on its own origin. Drupal submits the Content mapping's `search.parameter` (`keywords` on Drupal CMS) to its `search.path`, a relative path. Scoped to the `core/search` form's `action` and its input's `name`.
- Search result order differs: each backend ranks matches its own way. WordPress orders by its title-then-content relevance and then date. The search Template lists the Search API index's relevance order, and a `created` tie-break needs a sort field the Drupal CMS `content` index lacks. The same posts list on both sides. Scoped to the search Template's result list; each result's markup stays compared.
- Navigation labels differ: WordPress labels a Navigation block that references a navigation post with that post's title. WordPal binds that block to the mapped Drupal menu and prints the menu's label. Renaming the Drupal CMS `main` menu would edit config WordPal does not own. Scoped to a `wp-block-navigation` `<nav>` whose Drupal `aria-label` is a site menu's label, when WordPress prints an `aria-label` too.
- Page List navigation differs: WordPress's Page List prints every published page of the site. WordPal binds a Navigation block holding a Page List to the mapped Drupal menu and prints that menu's links in Page List markup, because listing pages is WordPress backend behavior. Scoped to the `href` and text of each `wp-block-pages-list__item` link inside a `wp-block-navigation` `<nav>`.
- Author links differ: WordPress links an Author Name to the author's archive for every visitor. Drupal links the author's user page only for a visitor with `access user profiles`, which Drupal CMS does not grant anonymous visitors. Granting it would change the site's access policy. Scoped to an author name whose only WordPress child is its link and whose Drupal side has no child element. The Author Name block's `wp-block-post-author-name` holds a `wp-block-post-author-name__link`. The Post Author block's `wp-block-post-author__name` holds an unclassed `<a>`. The computed-style comparison (ADR 0017) skips the same link, since it draws no box on Drupal's side.
- Empty Image links differ: a theme pattern can fill an Image's custom link in PHP, and Playground can leave it empty. YITH Wonder's My Account icon saves `<a href="">`. The Image component prints no link without a target. Scoped to an `<a href="">` that is a direct child of a `wp-block-image` element; its children stay compared.
- Inline link attributes differ: Canvas's `canvas_html_inline` text format keeps only `href` and the `data-entity-*` attributes on a link. A saved `rel`, `target`, class, or the link format's `data-type` and `data-id` drop at render, so the link loses `nofollow`, opens in the same tab on Drupal, or loses a class such as an animation hook. The text format is Canvas's config. Scoped to a WordPress `rel`, `target="_blank"`, class, `data-type` or `data-id` on a Drupal `<a>` with no class, style or other compared attribute.
- Placeholder links differ: WordPress sample content links to a bare `#`. WordPal's link props, such as the Button's `url`, declare `format: uri-reference`, because Canvas stores and edits such a prop as a link field. Core's link widget then accepts site paths and entity autocomplete. A prop without the format is plain text. Canvas validates the prop against that format, and `uri-reference` rejects `#`. WordPal writes no URL for that prop, so the Drupal link has no `href`. Scoped to a WordPress `href="#"` on an element whose Drupal side has no `href`.
- Plugin filters on core output differ: a WordPress plugin can filter the markup of a core block. WooCommerce's `paginate_links_output` filter adds `aria-label="Page N"` to each page number. Drupal does not run WordPress plugin PHP, so the Drupal page numbers carry no label. Scoped to a WordPress `aria-label` of the form `Page N` on an `a` or `span` with class `page-numbers`, when the Drupal element has no `aria-label`. cozy-addons' `render_block` filter adds `cozy-nav-hover-color` and `--cozy*` custom properties to a Navigation block's first `ul`. Scoped to that class and those properties on a `ul` whose WordPress side carries the class.
- Custom HTML differs: the `core/html` component renders its HTML through the WordPal HTML text format, so Canvas editors can change it without entering script. Drupal core's HTML filter drops every `style` and `on*` attribute, removes `<script>` tags, and drops tags outside the format's allow-list. No filter setting keeps `style`. `MarkupComparator` does not normalize these differences: parity reports them on pages whose Custom HTML carries them.
- A theme's own render filter differs: Blockskit Base hooks `render_block` in its own PHP to add both `uag-hide-mob` and `uag-hide-tab` classes to a block whose saved `className` already carries any `bk-hide-*` responsive-visibility marker (`bk-hide-mob`, `bk-hide-tab` or `bk-hide-desktop`). The saved markup and the block's own attributes hold no trace of the added classes; only the theme's PHP adds them, at request time, on live WordPress. WordPal converts the saved className and runs no theme PHP. Scoped to an element carrying a `bk-hide-*` class, where WordPress additionally prints `uag-hide-mob` or `uag-hide-tab`.
- Another theme's render filter differs: Charity Organization hooks `render_block` in `inc/block-filters.php`. It adds a `flex` class and a leading SVG icon to Post Date, Post Author and Post Terms, and an SVG icon inside a Post Navigation Link label. The saved markup holds no trace of them. Scoped to `flex` and the `<svg>` children of those blocks.
- A third theme's render filter differs: Spectra One hooks `render_block` in two files. `inc/extensions/header.php`'s `render_header` adds `swt-transparent-header` to a template part's wrapper from a custom `SWTTransparentHeader` attribute. `inc/extensions/responsive.php`'s `render_responsive_blocks` adds `swt-hide-mobile`, `swt-hide-tablet` or `swt-hide-desktop` to any block from its own `SWTHideMob`, `SWTHideTab` or `SWTHideDesktop` attribute. None of the four is a saved className; the saved markup holds no trace of them. Scoped to these four classes, wherever WordPress's reference render prints one.
- A fourth render filter differs: Kumitate hooks `render_block_core/group` in `inc/card-media.php` and prints a `siteframe-base-placeholder` figure with a theme SVG in a news card whose post has no featured image. It hooks `render_block_core/image` and `render_block_core/gallery` in `inc/main-visual.php` to give the first main visual image `loading="eager"` and `fetchpriority="high"`. The saved markup holds no trace of either. Scoped to an element with class `siteframe-base-placeholder`, and to the `loading` and `fetchpriority` of an image inside an `is-style-siteframe-visual` or `is-style-siteframe-slideshow` block.
- Older saved formats differ: WordPress prints a static block's saved markup as-is, so a theme can ship the output of an older save function. Components render only the current save function's output, which WordPress also writes the next time an editor saves the block. The comparator rewrites the WordPress reference into the current shape before it compares. A shape that only lacks a class the current save adds needs no rewrite, since a Drupal-only class drops out. Scoped to eight shapes:
  - Button typography on the wrapper instead of the link
  - a Button width saved as a bare `wp-block-button__width-<percent>` class
  - a Cover overlay before its saved image, and an overlay named `wp-block-cover__gradient-background`
  - a Cover background's `role="img"` with no `aria-label`
  - a resized Image's bare pixel `width` and `height` attributes
  - an Image width with no `height:auto` beside it
  - the deprecated `core/post-comments` block's wrapper class, `<h3>` heading and navigation-wrapped list, rewritten to `core/comments`'s wrapper class, `<h2>` heading and bare list
  - a Query's legacy flex `displayLayout`, which prints `is-flex-container` on a flow Post Template. The editor's migration saves a grid layout with the same columns, so the reference's `ul` takes the grid classes.

  The same rewrite runs on Drupal's side, where only a Frozen block prints saved markup. A further older format joins this list, never a component prop.
- Image lightbox markup differs: an Image block's lightbox, when enabled, runs WordPress's Interactivity API (`blocks/image.php`). It classes the figure `wp-lightbox-container`. It adds `data-wp-*` attributes to the figure and the image. It generates a `lightbox-trigger` button next to the image. Drupal core has no equivalent of this client-side reactive framework. Scoped to the `wp-lightbox-container` class, the `data-wp-*` attributes and the generated button, each on an Image's figure, image or lightbox button.
- An image in a Button's text differs: WordPress can save an `<img>` inside a Button's rich text. Canvas's `canvas_html_inline` text format is Canvas's own config. It allows no `img` tag, so the image drops from the saved text. Scoped to an `<img>` that is a direct child of a `wp-block-button__link` element.
- Honeypot spam protection differs: the `honeypot` module (`drupal/honeypot`) hides a `honeypot_time` field and a `url` textfield in the comment form. WordPress's public comment form sends neither. Scoped to the comment form's `honeypot_time` input and the div wrapping its textfield, named after the module's configured element name (`url` by default).
- The Archives and Categories dropdown's navigation target differs: WordPress values each `<option>` with a date key or a term slug and its inline script builds a query string from `home_url()` on change. WordPal values each option with the choice's own Drupal URL directly and navigates to it. Scoped to an `<option>`'s `value` inside a `wp-block-archives-dropdown` or `wp-block-categories-dropdown` element.
- Post Template row classes differ: `render_block_core_post_template()` renders each row as a `core/null` block that keeps the Post Template's attributes, so the elements support stamps the Post Template's `wp-elements-<hash>` class on the first element of every row. The `<ul>` carries the same class, so its link color reaches the same links. A `wp-elements-*` class on the first element of a `li.wp-block-post` is ignored.
- Duotone filters differ in place and scope: WordPress prints each duotone SVG filter in the page footer. WordPal prints a preset's filter right after the block, so a `<svg>` holding a `wp-duotone-*` filter is skipped. The computed-style comparison (ADR 0017) skips the same `<svg>` as an unpaired element. A custom duotone keeps no prop, because its colors are a list: its `wp-duotone-<colors>-<n>` class is ignored, and the image keeps its colors. That class's `<n>` comes from `wp_unique_id()`, a per-request counter with no fixed value across runs. Scoped to the image's `filter` computed style property, wherever the WordPress reference element's class matches `wp-duotone-<colors>-<n>` and Drupal's side carries no duotone class.
- Position containers differ in name: `wp_render_position_support()` names a sticky or fixed block's container `wp-container-<n>` with `wp_unique_id()`. WordPal names it after its rules. Both normalize to `wp-container-HASH`.
- Pagination numbers differ in their window: `paginate_links()` always prints the first and last page and `midSize` pages around the current one, with an ellipsis between. Drupal's pager centers a fixed window of pages. Matching WordPress means rewriting its paging, which WordPal leaves to Drupal. The matrix case for `midSize` stays reported.
- Image loading hints differ on Frozen blocks: WordPress adds `decoding` and `loading` to a template's images at request time (`wp_filter_content_tags()`), counting images across the page. A Frozen block prints the HTML its block rendered alone. Scoped to `decoding` and `loading` on an `img` inside a Frozen block's root.

## Considered Options

- Normalize the whole `wp-elements-*`/`is-style-*--HASH` class, variant name included. Rejected: the author chooses the variant name, and only the numeric suffix is request-scoped.
- Skip every unclassed `a`, `span` and `br` as sample-text formatting. Rejected for `a`: an unclassed anchor can still be a real link a **Conversion** dropped or changed. Tags that cannot carry structure on their own stay skipped.
- Ignore `id`, `title` and `aria-describedby` everywhere. Rejected: outside the comment form these carry real structure or accessibility meaning, and this milestone found no platform reason both sides cannot agree on them.

## Consequences

- A parity failure outside the contract rules, the generated-suffix rule and the exceptions above is a real difference between WordPal's output and the **Reference render**. Fix the code and leave the comparator unchanged.
- Amended by [ADR 0017](0017-appearance-equivalence.md): Markup parity is a diagnostic for work after the block matrix branch. There, an unlisted difference fails only when the computed styles or box geometry differ too.
- A newly found forced difference gets its own bullet here, scoped to where it happens, never a broader ignore rule.
- Amended 2026-09-30: a Conversion rewrites each **Platform credit** to strike WordPress through and link Drupal. `MarkupComparator` applies the same rewrite to the **Reference render** before comparing. A Canvas Conversion adds `<s>` to `canvas_html_inline` and the strikethrough item to its CKEditor 5 toolbar, and its Site recipe repeats both. The format's other limits above stay exceptions.
- Amended 2026-10-01: a Canvas Conversion also adds `<span class>` to `canvas_html_inline`, so a theme's classed span, such as a footer separator, survives render. The CKEditor 5 editor gains Source Editing, limited to `<span class>`, so an edit keeps the span. The Site recipe repeats both, and sets the editor's whole settings from the converting site. `<s>` and `<span class>` are the only changes WordPal makes to Canvas's text format.
- An exception that comes from a WordPress feature Drupal core lacks names the contrib module that provides it. A site closes that difference by adding the module as a dependency.
